# Каркас пояснительной записки к диплому

Тема: **«Многопользовательская браузерная игра реального времени на Rust»**
(рабочее название проекта: PoP - Protocol).

Ниже — структура глав с готовыми тезисами и указанием, какой материал проекта куда идёт.

---

## Введение (1.5–2 стр.)
- Актуальность: браузерные игры реального времени требуют согласованных решений в трёх плоскостях — сеть, физика, рендер; Rust даёт производительность сервера без ручного управления памятью.
- Цель: спроектировать и реализовать многопользовательский кооперативный арканоид (до 10 игроков) с серверной физикой, ботами и мета-системой.
- Задачи: протокол; сервер 30 Гц; лобби/реконнект; ИИ-боты; клиент 60 FPS; тестирование и нагрузочная проверка.
- Объект/предмет исследования, практическая значимость (работающий публичный код: github.com/LeviTankTV/PoPProtocol).

## Глава 1. Обзор предметной области и аналогов (5–7 стр.)
- Жанр arkanoid/breakout: история, механики (Brightly. *Arkanoid*; современные ремейки).
- Мультиплеерные модели: авторитарный сервер vs P2P; roll-back (GGPO) vs интерполяция — обоснование выбора авторитарного сервера с предсказанием только своей ракетки.
- Обзоры технологий: WebSocket vs WebRTC vs WebTransport; сериализация (bincode, protobuf, FlatBuffers) — выбор bincode + фиксированная ширина.
- Rust в игровой разработке: tokio, axum, экосистема; сравнение с Go/C++/Node для реального времени.
- Выводы по главе: обоснован стек Rust + axum + WebSocket + bincode + PixiJS.

## Глава 2. Архитектура системы (7–10 стр.)
- Общая схема: клиент (PixiJS 8) — WebSocket — сервер (axum/tokio) — MongoDB. *Схема из README (mermaid) превратить в рисунок 2.1.*
- Крейты: `popproto-core` (протокол, поле, генератор), `popproto-server` (лобби, игровой цикл, боссы, хранилище), `popproto-bot` (ИИ).
- Жизненный цикл комнаты: создание → ready-check → матч → возврат в лобби; реконнект с окном 90 с и АФК-ботом.
- Протокол v4: формат bincode little-endian фиксированной ширины; состав ClientMsg (15) и ServerMsg (16); дельта кирпичей + полный ресинк раз в 3 с (самовосстановление).
- Поток матча: PaddleX 40 Гц → фиксированные тики 30 Гц → снапшоты 30 Гц → интерполяция на клиенте.

## Глава 3. Серверная реализация (10–12 стр.)
- Физика: фиксированный шаг, сетка коллизий кирпичей, пулы мячей/капсул/пуль; потеря мяча, жизни, комбо-множитель.
- Адаптация поля под число игроков (ширина 800…1400).
- События (9): таймер 45–75 с, мгновенные (фонтан) и продолжительные, взаимодействие со скоростью/полем.
- Боссы (3): щиты-щупальца, снаряды-стан, ярость при 30 % HP; HP = 30 × живые игроки.
- Режимы: Кооп (15 уровней, финальная стена), Босс-раш (5 боссов подряд), Волна (процедурные ряды по детерминированному генератору, поражение = Exhausted).
- ИИ ботов: три уровня (реакция 9/4/1 тик, шум прицела 90/30/4, скорость); прогноз точки падения с отражениями от стен; steer-отскок в сторону центроида кирпичей; прицельный запуск.
- Хранилище: игроки, токены, XP; толерантное чтение Int32/Int64; MemoryStore для тестов.

## Глава 4. Клиентская реализация (8–10 стр.)
- Рендер PixiJS 8: слои (фон-кэш, кирпичи-кэш, динамика, тексты); кэширование статики — замеры «до/после» (гл. 6).
- Интерполяция: кубическая Эрмита по паре снапшотов вокруг `now − 1.6·Δt`; страховка выброса ±9 px; адаптивная задержка 50–140 мс.
- Предсказание своей ракетки: повтор серверной логики (скорость 760, клампы, стан), коррекция при расхождении > 60 px.
- Джус: стекло-кирпичи с детерминированными трещинами, шлейфы, кольца, комбо-фейерверк, генеративная музыка и SFX-синтез (WebAudio, без файлов), авто-деградация FX при FPS < 45.
- i18n RU/EN, мобильная вёрстка, палитра цветов, экран ачивок (👑🎯🧱🐙).

## Глава 5. Тестирование и обеспечение надёжности (5–7 стр.)
- 82 юнит-теста: физика, лобби/реконнект, боты, события, боссы, режимы, хранилище, протокол, генератор (таблица по модулям).
- E2E по WebSocket: `tools/ws-smoke.mjs` (полный цикл с реконнектом), `tools/xp-e2e.mjs` (цикл начисления XP).
- CI: GitHub Actions — fmt, clippy `-D warnings`, тесты, Docker-сборка; зелёный статус.
- Найденные и исправленные дефекты (таблица): типизация Mongo Int32/Int64; декодер Box<PlayerInfo>; TDZ-ошибка инициализации; потеря сетки кирпичей при реконнекте; флейк мгновенных событий; «уехать за экран» при широком поле.

## Глава 6. Исследование производительности (5–7 стр.)
- Методика: микробенч тика; стресс-тест 50 комнат × 10 игроков (tools/stress.mjs); замеры клиентского рендера.
- Результаты: таблицы из docs/PERFORMANCE.md — тик 4.8 мкс (0.014 % бюджета 30 Гц); 500 игроков: release 16.7 % ядра / 20 МиБ; эффект кэша клиента: медиана 15.0→5.8 мс.
- Вывод: узкое место — сеть (14 КиБ/с на игрока), физика имеет ~7000-кратный запас.

## Заключение (1–2 стр.)
- Все задачи выполнены; публичный репозиторий, CI, Docker-деплой.
- Перспективы: WebTransport, откат-неткод, турнирный режим, магазин косметики, мобильные приложения.

## Список источников (15–20)
Официальные документы: Rust Book, tokio, axum, WebSocket RFC 6455, bincode, PixiJS, MongoDB; статьи по неткоду (Gaffer on Games: Snapshot Compression, Networked Physics), GGPO/rollback; сравнение сериализаций; MDN Pointer Events; WebAudio API.
